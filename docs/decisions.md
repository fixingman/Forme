# FORME decisions

Last reviewed: 25 October 2026. This is durable project memory; changing status belongs in [project state](project-state.md). Dates below describe when a decision was recorded, not a claim of deployment.

Sources: user instructions in the October 20–22 project sessions, the memory plan approved on October 22, and the linked repository documents/code. Raw sessions contain private material and remain local. Where the user chose a goal but not its implementation, that distinction is explicit.

## Product and interface

**20–21 October — user direction, implemented in the local experience.** FORME is a personalized secondhand discovery app for mobile and desktop. Preserve the warm neutral palette and dark green navigation, with compact content and consistent Lucide icons. Keep the desktop sidebar collapsible. Reduce duplicate branding, introductory text and competing entry points.

- Home shows personal arrivals and observed price changes; Following covers followed brands; Discover recommends relevant brands outside those follows and explains its actual ranking rules.
- Use one global My sizes/departments editor beside Saved Items. Changes apply on confirmation; cancelling preserves preferences. Keep department chips consistent, including Not specified. Size matching stays conservative and category-aware, without invented international conversions. **24 October — user-approved refinement:** when an item's category cannot be classified, a letter size (XS–XXXXL, or a range of them) is still a clothing size, so one that is not among the owner's clothing sizes hides the item instead of passing as “unspecified”. This only ever hides: a matching size, and any numeric, waist or shoe size, still follow the include-unspecified setting. Underwear words (underwear, boxers, briefs, trunks, pyjamas, undershirt) and socks now classify as clothing. Socks are sized in European shoe sizes, so a sock size written as an EU range or number (40-43, EU 42) is matched against the owner's saved shoe sizes (same unit, no conversion); UK/US-labelled and S/M/L sock sizes, and any sock when no shoe size is saved, follow the include-unspecified setting. Source: owner request, 24 October.
- **24 October — user direction:** place piece feedback above the recommendation explanation on Discover cards (renamed **Not for me** in the later 24 October decision below).
- Cards show condition before size, omit missing-size filler, keep description text to one line, and display SEK once as `kr`. Do not restore the removed Sweden/SEK top-navigation pill or blanket limited-snapshot banner.
- Keep Follow → Neutral → Exclude ordering. Saved-search names are labels, not inferred criteria; new searches need an actual criterion. Browsing and preference changes filter existing data without paid requests.
- **24 October — user direction:** grid feeds reveal the next 24 pieces automatically as the reader approaches the bottom; replace the numbered Show more button. The Undo notification keeps its progress line and action, with no visible seconds counter (the owner explicitly clarified this refers to Undo).
- Collection diagnostics and experimental rarity/digest previews belong under Collection tools. Do not present unfinished experiments as supported core features.

Rationale: a clear shopping flow with fewer controls and honest recommendations. References: [core experience](core-experience.md), [README](../README.md), and the rendered shell in `components/forme.tsx`.

**23 October — user direction and implemented ranking policy.** Make Discover respond to the owner's taste using saved pieces, explicit/custom styles and reversible Not interested feedback. Keep ranking explainable and conservative: editorial brand/style references are starting points, title/category hints are inference rather than verified garment facts, and relevance weights never bypass department, size, exclusion, review or availability rules. Retained saved copies can supply signals when the original listing leaves the feed. Store a bounded summary of hidden-piece signals in optional profile data, compatible with v1 exports; restoration stops using that signal. Recommendation quality remains unmeasured, rather than proven by test coverage. Source: the owner's request to improve Discover; implementation details in [refresh and feedback](refresh-and-feedback.md#feedback-review).

A hidden saved piece stays saved, while its positive recommendation contribution pauses until restored. **25–26 October — performance fix after the owner reported the app rendering slowly (“it used to be faster”).** Measured cause: automatic training ran after almost every hide and on every feed view (24 runs in 25 minutes, each about 30–38 s of River plus Gorse and 320 MB), saturating the machine so the app's own learning and profile calls took 7–45 s, and leaving 5.6 GB of scratch folders. Fix, implementation policy and not a change to what is learned: automatic training is rationed (new feed pool or filters: about 5 s; new feedback on a feed that already has a model: at most every 20 minutes; nothing new: never), the manual Train button is unchanged, and old run folders are pruned (journal records are never touched). The 25 orphaned folders (5.5 GB, not referenced by the journal, no engine selected) were removed. Also: a stranded collection run (its server died mid-run) is now recovered whenever the status is read or a refresh is queued, instead of only by the optional worker, so it can no longer block refresh; its reservation stays counted and it is never retried. The collection that was cut off this way (54 of 96 searches, 270 credits charged, 528 listings saved) was left interrupted; continuing it needs a new quote and confirmation.

**26 October — user direction (“shouldn't we remove them from discover once they are fav.ed?”), implemented locally.** A piece you save leaves **Discover** (it is already yours); it stays in Saved items, and unsaving it there makes it a recommendation again. Reason for the change: a saved piece is the best possible match for the brand and style you just saved, so it scored highest and piled up at the top. The saved piece still counts as taste evidence (its brand, style and traits keep boosting similar pieces) and is still shown in Following, search results and its own page. Implementation: `recommendListings(..., {excludeSaved:true})`, used only by the Discover feed; Home, learning, the ranking preview, feedback review and collection planning keep the default, where saved pieces remain evidence. When nothing is left, the empty Discover explains where saved pieces went. Not done: there is no Undo toast on saving (a mis-tap is reversed from Saved items).

**26 October — fix for a stuck “Feedback kept on this device · N pending” notice (reported by the owner).** Measured cause: the browser's feedback queue sends oldest first and stopped at the first refusal, so one operation the server would never accept (50 exposures refused with “Exposure is outside its frozen pool”, after I had cleared the local learning history) blocked 54 others behind it, including real hides and reasons, and the notice stayed up. Implementation policy, not a change to what is learned: a refused **exposure** (400/413) is set aside at once and the next is sent; a refused **feedback event** is held in order and retried across flushes, and only set aside after 3 refusals, because a refusal can be a server race (one was observed and accepted on retry); temporary failures (offline, 401/403, 409, 503, 5xx) behave as before and discard nothing. Set-aside operations are kept for review (events whole, exposures as counts, newest 100 only) and the Learning page shows how many with a Discard button. Not diagnosed: why the browser sent exposures outside the frozen pool in the first place (a likely contributor is the feed showing pieces that were not in the run's pool); that is evidence-quality work for the learning loop.

**28 October — user approval (“I am open to only second”), implemented locally.** The owner asked why 299 feedback events still showed “insufficient evidence”. Measured on their real journal (read-only, counts only): 122 votes could count (saves and “Not my style” hides); 33 were scored; 89 had no frozen ranking attached (81 of them for pieces that were never in any Discover pool, because Discover ranks only brands the owner does not follow); the other hides carry reasons that are deliberately not taste-negative. The pair test also needs a save and a hide in one Discover visit, with a trained candidate already available when the visit began, over 5 days; the owner had 1 scored save. Of three options offered, the owner chose only the **second: use the dislikes**. Added a second, separate route to the evidence report (`dislikes` in `evaluateEvidence`; the pair route and its numbers are unchanged): for each frozen ranking where a candidate was available, the position (0 = top, 1 = bottom) of the pieces later hidden as “Not my style”, among the pieces that candidate had not trained on. A candidate qualifies on this route only if the day-level lower bound of that position is above the middle of the pool, it beats Current by at least 5 points, and there are at least 20 distinct pieces over at least 5 days (a pool under 10 or a candidate that did not rank the whole pool is skipped). The “above the middle” rule exists because hidden pieces were seen near the top of Current's order; beating Current alone would reward a reshuffle. It still needs the owner's separate approval to activate anything; no engine is selected. Replayed on the real journal: River places hidden pieces 75% of the way down against 39% for Current, but only 14 pieces over 2 days count (models were available in about 1 visit in 4), so it is not ready. Not done, offered: a plain “why votes were not counted” line on the page.

**28 October — user approval (“yes to 1 and 2”), implemented locally: hides are no longer lost to a sync conflict, and the lost ones can be brought back.** Measured on the owner's real browser: 196 hides in the older copy kept aside against 141 now; the 57 missing were all hidden within a 31-minute window on 27 October and all are still in the collection. Cause: the sync rule on a conflict is “the account copy wins, the local copy is kept aside”, so the hides made here since the last sync were dropped when another device had updated the account. Which device or session updated it is not known (the owner was unsure). Change: the rule is unchanged (the account's copy still wins) except that, **for the same account's own earlier sync only** (`pull-conflict` and a 409 on save), hides made here since the last recorded sync time (`forme-sync-at`, written after each successful sync) are carried across and sent up; the notice says how many. An older hide the account lacks is not carried (it was probably restored on purpose elsewhere), a hide with no date is never carried automatically, and a different account's earlier use of the browser, or a browser that never synced, is never merged. Restores made here and not yet synced are still overwritten by the account copy, and saves are not merged (neither has a timestamp). Recovery: Settings → Hidden pieces offers the older kept copy's hides back with their count (including undated ones, since the person is asking); either answer marks that kept copy as dealt with so a piece restored on purpose is not offered again.

**1 November — fix for a misleading “Local training: failed. Learning history is unavailable. Apply the learning migration or retry when connected.” (reported by the owner).** Measured: that one sentence was thrown for every failed read or write of the hosted learning history, although the tables exist and most calls succeed (the owner's page showed “Local training: complete” when checked; 179 of about 1,300 learning calls in the dev log returned 503, each after 15–49 s, in short bursts, which points at timeouts, not a missing migration). The real cause was discarded. Implementation policy, no change to what is learned or to retry behaviour: failures are now described by kind (missing table → asks for the migration; timeout; sign-in/permission; connection; other) and every kind stays a temporary 503, so the browser keeps and resends queued feedback exactly as before. The cause (operation, error code, short message, never row data) is now written to the server log as `learning.hosted.error`, so the next failure can be diagnosed. **Not fixed, and not the owner's fault:** why the hosted history is slow. Known contributors: every Discover view uploads a new full catalogue (about 2 MB; 195 stored since 25 October), and training reads all of them back. The parallel agent has an unfinished change that reads fewer catalogues; deduplicating or capping stored catalogues is a separate decision (it touches what evidence is retained).

**1 November — reviewed and committed: the parallel agent's unfinished change that stops the learning code downloading every stored catalogue (owner asked “do it” after asking what that uncommitted change was).** Measured before committing: the committed `status()` called `store.list("context")` on every call, whether or not training was allowed, so every status poll from the Learning page, and from the hosted site, downloaded all stored catalogues (195 at about 2 MB each); on the hosted store that read is paged 500 rows at a time, which is the likeliest source of the 15–49 s timeouts and the 503 “history unavailable” bursts. The change: (1) routine training and scheduling read only the newest catalogue per channel (`latestContexts()`, local and hosted) using an owner/channel/order index (`supabase/migrations/20261026000000_learning_context_lookup.sql`, an index only: no data, permission or policy change; the local SQLite store creates its own); (2) `status()` no longer reads catalogues at all; (3) full exports still read every catalogue, one per request, so nothing is lost; (4) catalogue and filter identity now use canonical JSON hashing (`canonical-json-v1`), because a database JSON column reorders object keys, so a stored catalogue used to hash differently from the same feed freshly built, which in hosted mode could stop a trained model matching the current feed (this fits the earlier finding that models were “unavailable” at the start of most visits). The persisted feature-signature hash is deliberately unchanged. Consequence: runs recorded before this change carry the old hash, so the first feed view afterwards will not find a matching model and one automatic retrain follows. **Historical deployment report, unresolved as of 2 November:** this session reported the migration as not applied, conflicting with the 26 October report of live application and verification. Inspect live index metadata before reapplying. The project works without it (it only makes the newest-catalogue lookup faster), and creating the index reads each stored catalogue once and briefly blocks writes to that table. Nothing is pruned. Capping or deduplicating stored catalogues is still a separate decision. The same parallel-agent files also hold unrelated unfinished work (a “fit” reason, the dashboard and Discover-continuity edits); none of that is included.

**2 November — user direction (“do 1,2 and remove 3”), implemented locally: three changes that follow from the owner's finding that the silent test was measuring far fewer votes than they cast.** Measured on the owner's real journal (read-only, counts only): of 190 saves and “Not my style” hides, 47 were linked to a frozen ranking. By cause: 88 were on brands the owner follows, which Discover never ranks (by design); 72 were cast on 31 October, when the ranking requests stopped getting through (a vote cast then had no ranking on screen); 8 were mostly cast before a model was ready; 1 unexplained. Unlinked votes are dropped, not counted against any model, so they shrink the evidence without skewing it. **(1) One ranking per visit.** The client re-requested a ranking, uploading a fresh catalogue of about 2 MB, on every change to the preferences, so on every vote; the answer was then discarded unless a learned version was selected. That produced the 195 stored catalogues and probably the slow history that lost votes. Now the request depends on the feed itself (pieces, departments, sizes, followed and excluded brands, styles) and on a new visit; while a learned version is selected, a vote still refreshes it, because whether that version applies depends on the votes. **(2) A plain account of uncounted votes.** `evaluateEvidence` now reports, for each save or style hide that was not scored, why, using the same checks and order as the scoring (no ranking on screen, a record that never arrived, outside the window, an older rule, cast before the ranking was saved, a piece the models trained on, not among the ranked pieces), plus the brands of the votes that had no ranking; the Learning page shows “N of M votes are counted” with the reasons and how many were on followed brands. **(3) The private ranking preview and the Learning page's “Create learning comparison” were removed** (the owner never used them and did not expect to): the page, its API route, server module, model script, seeding script, tests, styles and docs, and the analyst's “Private preview” source. Kept on purpose: the server still accepts a `preview` channel and `comparison` snapshots (tests and old records rely on them) and the one ranking-normalising rule the learning code uses (`lib/domain/ranking-preview.mjs`); nothing in the app creates preview data now. Private data from earlier preview sessions under `.context/ranking-preview/` is left in place for the owner to delete. The activation approval no longer has a “private-preview consent” box, because activation can only come from shopping evidence now.

**4 November — user direction (“we should remove the sold items from the fav”; of three options offered the owner chose A), implemented locally.** Saved pieces that a provider check has confirmed are gone (sold, or removed or hidden on Vinted) are listed apart in a **“No longer available (N)”** group at the bottom of Saved, with a **Remove from Saved (N)** button that asks first. Nothing is removed on its own. Reserved pieces stay with the rest (a reservation may lapse), and a piece that merely stopped appearing in searches is never treated as gone (absence from a limited search is not proof of sale; data-trust rule). The main list and the count exclude the gone pieces; the group shows only pieces the current filters show. **Known limit:** the app currently knows of no sold piece, because no listing in the collection (3,035) has a provider-confirmed availability and none of the 12 saved pieces had ever been checked; collection searches carry no sold flag. The group fills only after the paid availability check (Collection tools → Refresh → saved items; one item-detail call each, up to 10 credits, 3 per run). Implementation: `lib/domain/saved-split.mjs`, `components/saved-unavailable.tsx`, `removeSaved` in `forme.tsx`.

## Accounts and private beta

**21–22 October — user-approved direction.** Use Supabase for Postgres and authentication. The beta is single-owner across desktop and mobile, invite-only, passwordless, with collection restricted to the owner. No friend onboarding is required for the initial beta.

**22 October — implemented approach, real setup pending.** Commit `2088962` adds email-link and Google sign-in paths, invite checks, database row-level security, revision-based profile sync and hosted listing reads. Email links are the documented baseline; Google configuration is optional. The earlier planning note that authentication/sync were unimplemented is superseded by this code, not by evidence of a live deployment.

- Collection, translation and publishing remain on the owner's computer. The service-role key stays there; browser sessions cannot publish listings.
- Preserve local preferences and JSON exports. Sync can adopt an existing account profile, retaining the prior browser copy; concurrent edits use revision checks rather than silent overwrites.
- Vercel remains the documented hosting direction, not a provisioned service. Inngest/a hosted durable worker and a distributed spending ledger remain proposals for later work, not selected dependencies to add automatically.

**23 October — user decision.** Do not enable Google sign-in for now; email links only. The login page hides the Google button unless `FORME_GOOGLE_SIGNIN=1`, and `/auth/google` refuses while it is off. This narrows the earlier "email link or Google" direction; it can be reversed by setup alone.

**23 October — user decision.** Send sign-in email through Resend over SMTP, using Resend's shared test sender because the owner has no domain to verify. This delivers only to the Resend account's own address, which suffices for a single owner; it is a stopgap, not a deliverability plan. A key pasted into chat is treated as exposed and must be revoked; keys go only into Supabase's SMTP password field.

Rationale: cross-device use without building password handling or prematurely moving paid collection into the cloud. Reference: [accounts setup, sync behavior and limitations](accounts-setup.md). Both passwordless paths now exist in code; which providers to enable in the real project remains a setup choice.

**25 October — user-requested simplification of the item page, implemented.** Make the item page's metadata and actions simpler and consistent with cards, without a redesign. ## Data trust

**21 October — implemented policies to preserve.**

- Retain marketplace identity, provenance, original text and per-item source observation times. Merging an old row into a fresh snapshot must not make that row newly observed.
- Department can come from explicit provider fields, explicit title wording or documented search scope. Never infer it from brand, size, silhouette or photos; distinguish search scope from item-level evidence.
- Style inference is allowed with visible evidence. Collectible title signals stay separate from verified rarity; never invent scarcity scores or live rarity badges.
- Unknown availability stays unknown. Missing limited-search results do not prove sale or removal. Explicit sold/unavailable observations retain their provenance and must survive later search refreshes.
- New to FORME describes first observation, not seller publication today. Price changes require actual stored observations. Demo claims remain fictional and distinct from live data.
- Keep exact-title English translation caches and originals. Uncached text remains pending; do not imply that collection includes paid translation.
- Validate public fields and outbound URLs; discard seller payloads. Do not silently replace failed live data with demo results or weaken filters to populate an empty feed.
